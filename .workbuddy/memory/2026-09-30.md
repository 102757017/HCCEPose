## s2 GT masks 多进程崩溃修复（Windows spawn + pip bpy）
- 现象：`bproc.writer.write_bop(num_worker=4)`（Calculating GT masks/info）在 Windows 上 spawn 子进程崩溃 `ModuleNotFoundError: No module named '_bpy'`；`num_worker=0` 串行可跑但极慢。
- 根因：pip bpy wheel import 时前插 5 个 `site-packages/bpy/3.6/scripts/*` 路径到 sys.path；Windows spawn 把 sys.path 原样传子进程并 runpy 重跑主脚本，`import bpy` 被抢先解析到 scripts/modules 纯 Python 包（`from _bpy import ...` 在 pyd 引导前执行）。
- 修复：`blenderproc/python/writer/BopWriterUtility.py` 新增 `_patch_spawn_sys_path_for_bpy()`（monkeypatch `multiprocessing.spawn.get_preparation_data`，只过滤发给子进程的 sys_path 副本），`_start_mask_worker_pool` 开 Pool 前调用；父进程 sys.path 不动，Blender 运行时不受影响。
- 验证：仓库根 `test_spawn_bpy_syspath.py`——带补丁 PASS（子进程 import bpy 成功），`--no-patch` 对照复现原始崩溃。`get_preparation_data` 调用点是 `popen_spawn_win32.py:47` 模块属性查找，monkeypatch 可行。
- 关键认知：干净解释器里 `import bpy` 的最终归宿本来就是 scripts/modules 纯 Python 包（pyd 先加载引导、注册 _bpy、随后被纯 Python 包接管 sys.modules），"bpy.__file__ 指向 .py" 是常态；判据是 import 成败，且引导完 `_bpy` 不留在 sys.modules。
- 注意：用户实际运行 checkout 在 E:\python\HCCEPose（另一台机器），F: 工作区的修改需手动同步过去。
- 后续：修复在用户 E: 环境生效后，4 个 worker 各自 import pyrender 时刷 PyOpenGL 的 import 期诊断（`OpenGL.acceleratesupport` INFO + `OpenGL.GL.shaders` DEBUG，均无害）。已在 s2 脚本 basicConfig 后加 `logging.getLogger("OpenGL").setLevel(logging.WARNING)` 压噪（不影响脚本自身 DEBUG 耗时日志）。PyOpenGL-accelerate 未装：PyOpenGL 3.1.0 配对的 accelerate 3.1.0 无 cp310 win wheel，升级 3.1.10 会动冻结栈，决定不装（收益仅 worker 端少量 GL 调用开销）。
